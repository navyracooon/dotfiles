# PR レビュー対応の手順と PRF 体裁

PR に付いたレビューコメントへ対応するときは、以下に従う。

## 全コメントの収集

`gh pr view --json reviews,comments` だけでは**本文コメントを取り落とす**。次の 3 面を必ず列挙する。

- inline レビューコメント: `gh api --paginate repos/{owner}/{repo}/pulls/{n}/comments`
- 本文（issue）コメント: `gh api --paginate repos/{owner}/{repo}/issues/{n}/comments`
- レビュー本体: `gh api --paginate repos/{owner}/{repo}/pulls/{n}/reviews`

収集後、レビュアーごとの件数を数えて依頼者に提示する。人間のコメントと、bot や AI が生成したレビューを区別して扱う。

## 対応の順序と粒度

コメントが提示された順に上から 1 件ずつ扱う。指摘の重さで並べ替えない。依頼者が「この件は修正不要」と判断したものは飛ばす。

**1 コメント = 1 コミット**に切り分ける。複数の指摘を 1 コミットに混ぜない。修正が不要と判断した件はコミットを作らず、判断理由を報告に含める。

レビュー指摘とコミットの 1 対 1 を崩さない。指摘と無関係な修正は、指摘に対応するコミットへ混ぜず、独立したコミットとして切り分ける。ただし、その指摘のコミット自身が入れた記述の直し（コメントの言い換えなど）は、まだ push していなければ元のコミットに畳む。

コミットメッセージは、指摘された事象と、なぜその修正が正しいかを述べる。レビュアー名や「レビュー指摘対応」という言い方は使わない（成果物の説明であって経緯ではない）。

## 検証

主張は実測してから受け入れる。**検証の結果「修正不要」となることもある**前提で臨む。

- ライブラリの挙動は使い捨ての probe を書いて測り、測定後に削除する
- 数値の主張は自分で計算し直し、提示値と一致するか確かめる
- 「既存はこうなっている」という主張は、リポジトリを数えて確かめる（件数を出す）
- デザインの逸脱は、デザインツールの原本を引ける環境なら直接引いて確かめる
- 相手の数値に誤りがあっても、結論が変わらないなら「結論は不変」と明記して受け入れる

検証できない主張は、できないことを述べる。

## セルフレビュー（SR）

全コメントのコミットを積み終えたら、PRF 体裁で提示する**前に** `../self-review/SKILL.md` に従って SR を行う。対象は今回積んだ全コミットの差分（`git diff origin/<branch>..HEAD`）。

- SR で見つけた問題のうち、その指摘のコミット自身が入れたものは、push 前なら該当コミットに畳む（`--fixup` + `rebase --autosquash`、HEAD なら `--amend`）。指摘と無関係な問題は独立したコミットに切る
- SR の後に lint・テスト・生成物の再確認をやり直す。畳んだ結果に対して測り直していない数値を報告に使わない
- PRF の前に、SR の結果を観点ごとに 1 行ずつ（確認したこと・実測値・直した箇所）まとめて置く。問題が無かった観点も「何をどう確認したか」を残す

SR を経ていない PRF は提示しない。

## PRF 体裁（PR Fix 体裁）

全件について、コメント 1 件ごとに次の三部構成で報告する。依頼者が「PRF 体裁で」と呼び出したときも、対応済みの内容をこの様式で提示する。

PRF の対象は **PR 上のレビューコメントだけ**である。依頼者からの指示は PRF の項目にしない。通常の報告として書く。

PRF と SR の要約の地の文は AGENTS.md の Writing 節に従う。三部構成と見出しは崩さず、その中の文だけを合わせる。レビュアーへの返信は対象に含めない。

    # {レビュアー}-{番号} → `{コミット SHA}` {一行の要約}

    ## コメント内容

    指摘を要約する。引用の丸写しではなく、主張と根拠と提案を圧縮する。

    ## 検証

    何をどう測り、結果がどうだったかを述べる。数値は数値で書く。
    「指摘は正確です」「一点だけ誤りがありますが結論は不変です」など、判定を明示する。

    ## 修正前後

    **コードの原文を必ず載せる。** 散文で言い換えるだけにしない。
    形式とパスのリンクは `../code-citation/SKILL.md` に従う（置換・削除があれば差分、追加のみなら本文だけ）。

    ファイルが複数あるときは、ファイルごとに小見出しを付けて分ける。
    テストの追加件数と内容、テスト実行結果を末尾に書く。

## Push

**明示的な承認があるまで push しない。** 報告後、依頼者の指示を待つ。

push 前であれば、指摘を受けた再修正は `--fixup` + `rebase --autosquash` で該当コミットに畳んでよい。push 後は追加コミットで積む（履歴を書き換えない）。

再修正のたびに、変更した箇所を含めて**全件を PRF 体裁で再提示する**。差分を省略しない。

## 最終段階

依頼者が「最終段階へ」と告げたら、push 前の最後の提示として次を出す。

- コミット 1 本ごとに、対応するレビュー指摘（または指摘外である旨）と一行の内容
- 修正不要と判断した指摘の一覧と、その理由の要約
- 未 push であることと、remote との差分の規模
- 検証の結果（テスト件数、lint、実測した数値）
- push 後に残る作業（別 PR に回した件、他リポジトリのマージ順など）

差分は再掲しない。直前の PRF 体裁で提示済みのため、ここは対応表と状態の確認に絞る。

**依頼者の承認を受けてから push する。** 承認の言葉がない限り、この段階で止まる。
