# セルフレビュー（SR）

SR は書いた本人の側が自分の差分を点検する段である。後に続く UR（`../user-review/SKILL.md`）は依頼者が判断する段なので、SR で潰せるものを UR に持ち込まない。

対象は、これから PR にする、または Draft で出したばかりの差分の全体と、その PR 本文（「8. PR 本文」）である。基準は remote に取り（`git diff origin/<base>...HEAD`。ローカルの base は古いことがある）、頭から 1 ファイルずつ読み直すところから始める。

**Ready にする前に積んだコミットは、すべて SR を通す。** SR の後に積んだもの（UR 中の修正、指摘への対応）は、追加分のコミットだけをもう一度通す。PR 全体との整合は毎回見る。コメントの追加は 1 行でも通す。PR 本文を書き換えたら、本文も通す。UR で依頼者の目を通ったことは SR の代わりにならない。

## 実行形態

SR は別エージェントで行う。起動と渡し方は `../separate-agent/SKILL.md` に従い、指定がなければ PA で起こす。

親が渡すもののうち、SR に固有のものは次のとおり。

- チケットのキーと、取得済みなら AC の原文。参照手段があればエージェント側でも再取得させ、親の理解と食い違えば報告させる
- PR の番号と URL、比較基準（`origin/<base>`）、依存 PR が未マージなら統合ブランチの worktree のパス
- PR 本文。PR がまだ無ければ、作る予定の本文の下書きをファイルにして渡す。本文を渡さずに SR を終えない
- 制約への追加: PR にコメントせず、本文も編集しない
- 本スキルのパス（この「実行形態」節と「SR ループ」節は親向けなので、エージェントは読み飛ばす）

エージェントは「7. 修正と報告」の報告と修正コミットの一覧（SHA と件名）を返し、修正は worktree にコミットとして残す。親は修正コミットを `git show` で確かめてから、要点を依頼者へ伝える。

## SR ループ

「SR ループで」と依頼されたら、SR の指摘を直し、その修正をまた SR にかけることを、指摘が 0 件になるまで繰り返す。

- 各回は新しい別エージェントで起こす。前の回のエージェントは自分の修正を書いた本人である
- 2 回目以降の対象は、前の回の修正コミットである
- 数えるのは「見つけた問題」だけで、環境や認証の都合による未了事項は数えない。数えるとループが終わらない
- 終了条件は、ある回で修正コミットが 1 つも積まれないことである
- 前の回の修正を戻す指摘や、同じ箇所を行き来する指摘が出たら、ループを止めて依頼者に判断を預ける

依頼者への報告はループの終了後にまとめ、回ごとの指摘の件数と修正コミット、最後の回で 0 件になったことを示す。

## 1. 要件との突き合わせ

チケットの AC（無ければ依頼文の要求）を 1 項目ずつ列挙し、各項目に「満たす実装（diff のどこか）」と「裏付ける検証（どのテスト・実測か）」を対応付ける。

裏付けが無い項目は、次のいずれかに必ず落とす。

1. テストを足す（AC が検証可能な形なら原則こちら）
2. 使い捨ての probe や手元のコマンドで実測し、数字で控える
3. 今できないものは未了として PR 本文（マージ条件の欄など）に書く

スコープ外と明記された項目に手を出していないかも同時に見る。

## 2. コメントの過不足

過剰コメントはよくあるミスという前提で、AGENTS.md の Editing 節の基準（同じ層の既存コメントの行数と調子を実測して合わせる、根拠の二重記載・言い直し・無関係な補筆を削る）で 1 つずつ疑う。行数が隣接に収まっていることは必要条件にすぎない。

各文を「契約・制約・意図（コードから読めないこと）」か「経緯・比較・帰結・言い換え」かに分け、前者だけを残す。後者の典型は次のとおり。

- interface と実装の doc の重複。契約は interface 側に一本化し、実装側は実装層でしか分からない機構だけを書く。同種の隣接実装がコメントを持たないなら実装側は無しにする
- 存在理由（「Y は重いので足した」）と兄弟との比較（「Y と違って…」）
- 帰結の語り（「そうしないと画面が欠ける」）
- 他チケットや未実装の将来挙動への前方参照。スキーマの列コメントも現時点の事実だけにする

チケット参照の書き方と位置は既存の慣習に合わせる。

不足の典型は、呼び出し側が知らないと事故る前提・副作用・失敗時の倒れ方（fail open / closed）が、コードから読めない場所に書かれていないことである。

## 3. 実装の過不足

- 過剰: 使われない引数・戻り値、今回使わない汎用化、依頼と無関係な修正、既存と重複する新規ヘルパー（既存を数えてから足したか）
- 不足: AC が要求するのに無い挙動、エッジケース（空入力、再実行・再配信、境界値）
- 一貫性: 命名、エラーハンドリング、トレーシングの型が同じ層の隣接コードと揃っているか

## 4. テストの過不足

UR ではテストを提示しないので、テストが変更を固定できているかを見るのはここだけである。「書いた、通った」では足りない。

不足の検出:

- **変更した分岐を数え上げ、1 つずつ固定しているテストを対応付ける。** 表に足した行、`switch` の `case`、早期 return、wrapper の素通し経路をそれぞれ 1 件と数える。対応が無いものはテストを足すか、足さない理由を報告に書く
- **赤になることを確かめる。** 実装を戻すか条件を 1 つ崩してテストを回し、落ちるのを見る（probe は使い捨て）
- 公開した関数・型の約束（未登録の入力に `nil` か既定値か、上書きか素通しか）を固定する
- エラー経路と境界。既存テストが正常系だけのパッケージでは、変更した異常系がそのまま漏れる

過剰の検出:

- 表や分岐をテスト側で再定義して突き合わせるだけのテストは、実装と一緒に変わるので何も固定していない
- 下位で固定した分類を上位でも全件並べ直していないか
- ライブラリの挙動を確かめるテストは、こちらの変更を固定しない
- テーブル駆動の行は件数ではなく、通る経路の数で数える
- 固定したい 1 点に対して helper、mock、fixture が大きすぎないか

書き方（table-driven か、`assert` と `require`、サブテスト名、golden）と置き場所は、同じパッケージの既存テストに合わせる。外部依存を要するテストは `TestMain` の前提に沿わせる。前提を欠いたまま黙って通るテストは無いのと同じである。

## 5. 手元での動作確認

- 変更したパッケージのテストと lint を実際に実行し、結果を数字で控える。SR の合否はこの手元の結果で決め、GitHub の CI は待たない（待ち方は `../ci-check/SKILL.md`）
- lint の指摘は自分の変更起因か既存問題かを切り分け、既存問題には手を広げない
- ガード系のテスト（不変条件の検査）は、同型の「既にその状態にある対象」へ同じ検査を当て、本当に落ちることを見る（negative probe）
- 生成物は正規の生成コマンドで再生成し、差分が出ないことを確かめる

実環境での確認は `../verification/SKILL.md` が扱い、SR の合否とは独立に PR 本文へ積む。

## 6. 意図しない差分

- 無関係なファイル、空白や改行だけの変更、一時ファイルが混ざっていないか
- 依頼と無関係な既存行（末尾空白の除去なども）を巻き添えにしていないか
- 機微データや認証情報が、テストデータ、ログ出力、その連携先に乗っていないか

## 7. 修正と報告

見つけた問題は観点ごとに独立したコミットに切って直す（コメント整理と挙動追加を混ぜない）。コミットメッセージは最終状態を説明し、「セルフレビュー対応」のような経緯は書かない。エージェントは worktree にコミットを残すところまでで、push と PR 作成は親が行う。

報告は観点ごとに三部で書く: 確認したこと（実測値つき）／見つけた問題／修正の diff。問題が無かった観点も、何をどう確かめたかを 1 行残す。未了事項は報告と PR 本文の両方に書く。手元のテストと lint の結果は報告にだけ残し、本文へは渡さない（`../pull-request/SKILL.md`）。

## 8. PR 本文

本文はレビュアーとチームが読む成果物で、差分と同じく SR の対象である。

- 最終状態との一致: 本文の主張（変更の内容、影響範囲、Verification の観測値）を差分と実測に突き合わせ、直したのに古いままの記述、測った値と合わない記述を探す
- 書き方: `../pull-request/SKILL.md` と AGENTS.md の Writing 節に照らす。作業の過程（評価やレビューで何が挙がり、どう対処したか）を語る文、手元の環境の固有名（ローカルのテナント名やユーザー名）、変更の正しさに要らない「未確認」を探す。過程を語る文は、結果として残る事実（「〜は自動テストで固定していない。〜で確かめている」）に書き直すか、レビュアーに要らなければ削る

本文の修正は、報告の「修正の diff」に本文の差分として書く。本文の編集は親が行う。

## 次の段

SR の後は Verification（`../verification/SKILL.md`）を済ませ、依頼者が「UR を」と告げてから UR に入る。自分から UR を始めない。
