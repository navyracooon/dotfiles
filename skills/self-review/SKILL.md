# セルフレビュー（SR）

レビューは 2 段ある。**SR**（セルフレビュー）は書いた本人が自分の差分を点検する段で、本スキルが扱う。**UR**（ユーザーレビュー）は依頼者がレビュアーとして読む段で、`../user-review/SKILL.md` が扱う。SR で潰せるものを UR に持ち込まない。

自分の変更をレビューに出す前に、以下を上から順に行う。対象は「これから PR にする、または Draft で出したばかりの自分の差分」全体と、その PR 本文（「8. PR 本文」）。`git diff`（コミット済みなら `git show` / `git diff origin/<base>...HEAD`。ローカルの base ブランチは古いことがあるため基準は remote に取る）を頭から全部読み直すところから始める。流し読みではなく、書いたときと別の目で 1 ファイルずつ読む。

## SR を通すのは Ready までに積んだ全コミットである

**SR の後に積んだコミットは、それ自体が SR を通っていない。** UR の途中で入れた修正、依頼者の指摘への対応、他の PR の SR を受けて直した箇所も同じで、Ready にする前にもう一度 SR へ回す。

回すのは差分の全体ではなく**追加されたコミットだけ**でよい。ただし PR 全体の文脈との整合は見る。とくにコメントの追加は、行数と調子が慣習に収まっているかという SR の主眼に当たるので、1 行でも通す。PR 本文を書き換えた場合も、Ready の前に本文を SR へ回す。

UR で依頼者の目を通ったことは SR の代わりにならない。UR は依頼者が判断する段で、慣習との突き合わせや実測は SR の仕事である。

## 実行形態

SR は差分を書いた本人のコンテキストでは行わず、**別エージェント**に任せる。書いた文脈には「なぜそう書いたか」が残っており、その文脈で読み直しても書いたときと同じ目にしかならない。起動は `../separate-agent/SKILL.md` に従い、**指定がなければ PA** で起こす。依頼者が別の指定をしたときだけそれに従う。

親（本体のセッション）が渡すもの:

- チケットのキーと、取得済みなら AC の原文。参照手段があればエージェント側でもチケットを再取得させ、親の理解と食い違えば報告させる
- PR の番号と URL、比較基準（`origin/<base>`）
- PR 本文。PR がまだ無ければ、作る予定の本文の下書きをファイルにして渡す。本文を渡さずに SR を終えない
- 作業場所。既存の worktree があればそのパス（PR ブランチのものと、依存 PR が未マージで統合ブランチ上で試験する場合はそのパスも）。無ければ worktree を切らせる（Claude Code なら `isolation: "worktree"`）
- 守らせる制約: push しない、PR にコメントせず本文も編集しない、本体クローンと他の worktree に触らない、無関係な未コミット変更を扱わない
- 本スキルのパス。エージェントは本スキルを読んでから始める（この「実行形態」節は親に向けたものなので、エージェント側では読み飛ばす）
- エフォート（規定 High）。親の仮説と結論は渡さない（`../separate-agent/SKILL.md`）

エージェントが返すもの: 「7. 修正と報告」の三部形式の報告と、修正コミットの一覧（SHA と件名）。修正は worktree にコミットとして残す。

親は報告を転記せず要点を依頼者へ伝える。その文は AGENTS.md の Writing 節に従って書く。修正コミットは自分で `git show` して確かめ、push は依頼者への報告後に既存の規則に従って親が行う。

## SR ループ

**SR ループ**は、SR の指摘を直し、その修正をまた SR にかけることを、指摘が 0 件になるまで繰り返すことを指す。「SR ループで」と依頼されたときに行う。

- 各回の SR は**新しい別エージェント**で起こす。前の回のエージェントは自分の修正を書いた本人であり、その目で読み直しても書いたときと同じ目にしかならない
- 2 回目以降の対象は、前の回で積まれた修正コミットである（「SR を通すのは Ready までに積んだ全コミットである」）。PR 全体の文脈との整合は毎回見る
- 指摘として数えるのは「7. 修正と報告」の「見つけた問題」だけである。環境や認証の都合で今できない未了事項は数えない。数えると、直しようのない項目でループが終わらなくなる
- 終了条件は、ある回の報告で見つけた問題が 0 件、すなわち修正コミットが 1 つも積まれないことである
- 前の回の修正を戻す指摘や、同じ箇所を行き来する指摘が出たら、ループを止めて依頼者に判断を預ける。判断の分かれる箇所はエージェントを替えても収束しない

親はループの間、各回の報告を受けるたびに修正コミットを `git show` で確かめてから次の回を起こす。依頼者への報告はループの終了後にまとめて行い、回ごとの指摘の件数と修正コミット、最後の回で 0 件になったことを示す。push はその後、既存の規則に従う。

## 1. 要件との突き合わせ

チケットの Acceptance Criteria（無ければ依頼文の要求）を 1 項目ずつ列挙し、各項目に次の 2 つを対応付ける。

- **満たす実装**: diff のどこがその項目を満たすか
- **裏付ける検証**: どのテスト・実測がそれを証明するか

裏付けが無い項目は、次のいずれかに必ず落とす。曖昧なまま「実装したので満たしているはず」とはしない。

1. テストを足す（AC が検証可能な形で書かれているなら、原則こちら）
2. 使い捨ての probe や手元のコマンドで実測し、結果を数字で控える
3. 環境や認証の都合で今できないものは「未了」として PR 本文（マージ条件の欄など）に明記する

スコープ外と明記されている項目に手を出していないかも、ここで同時に見る。

## 2. コメントの過不足

**過剰コメントはよくあるミス**という前提で、書いたコメントを 1 つずつ疑う。判断基準は自分の感覚ではなく**プロジェクトの慣習**の実測で、隣接関数の行数レンジに収まっているかは必要条件にすぎない。同じパッケージ・同じ層のコメントを一通り読み、長さだけでなく調子（要約 1 行で止めるか、根拠まで書くか、経緯を書かないか）を測る。1 箇所にしか書かないコメントであっても、プロジェクトの調子より丁寧で冗長なものは削る。

行数が収まっていても削る対象:

- **根拠の重複**。同じ理由を 2 箇所（関数 doc と inline、コメントとエラーメッセージ、コメントとコミットメッセージ）に書いている。1 箇所に残す
- **読めることの言い直し**。エラーメッセージ、テスト名と入力値、assert の文言、識別子から読めることを繰り返している
- **指摘・変更と無関係な追加**。既存関数に doc が無いのを見て足す、といった依頼範囲外の補筆

削る典型:

- **interface と実装の doc 重複**。契約（目的・前提・副作用）は interface 側に一本化し、実装側は実装層でしか分からない機構（トランザクションの畳み方など）だけを書く。同種の隣接実装がコメントを持たないなら実装側は無しにする
- コードの言い換え（処理をなぞるだけのコメント）
- 経緯の説明（「X という問題があったので Y にした」）。書くなら「X を回避する」と結果だけを書く
- 存在理由（「Y は重いのでこのメソッドを足した」）と兄弟メソッドとの比較（「Y と違って…」）
- 帰結の語り（「そうしないと画面が欠ける」）
- 他チケット・未実装の将来挙動への前方参照（「後続の Z で差し替える」）。スキーマやデータ定義の列コメントも現時点の事実だけにする

判定は行数チェックとは別に、コメントの各文を「契約・制約・意図（コードから読めないこと）」か「経緯・比較・帰結・言い換え」かに分類して行う。前者だけを残す。

合わせる典型:

- チケット参照の書き方と位置を既存の慣習に合わせる
- コメントの行数レンジを隣接に合わせる（隣が 0〜2 行なら 5 行書かない）

不足の典型: 呼び出し側が知らないと事故る前提・副作用・失敗時の倒れ方（fail open/closed）が、コードから読み取れない場所に書かれていない。

## 3. 実装の過不足

- 過剰: 使われない引数・戻り値、今回使わない汎用化、依頼と無関係な修正やリファクタ、既存コードと重複する新規ヘルパー（既存を数えてから足したか）
- 不足: AC が要求するのに無い挙動、エッジケース（空入力、再実行・再配信、境界値）の未処理
- 一貫性: 命名・エラーハンドリング・トレーシングの型が同じ層の隣接コードと揃っているか

## 4. テストの過不足

**UR ではテストを提示しない**（`../user-review/SKILL.md`）。テストが今回の変更を固定できているかを見るのは SR だけで、ここを通したものは誰の目にも触れない。「書いた、通った」では足りず、必要十分であることを確かめる。

必要（不足の検出）:

- **変更した分岐を数え上げ、1 つずつ固定しているテストを対応付ける。** 表に足した行、`switch` に足した `case`、早期 return、wrapper の素通し経路は、それぞれ 1 件として数える。対応が無いものはテストを足すか、足さない理由を報告に書く
- **赤になることを確かめる。** 実装を元に戻す、または条件を 1 つ崩した状態でそのテストを回し、落ちるのを見る。通ることしか見ていないテストは、変更を固定している証拠にならない（probe は使い捨てにする。「5. 動作確認」のガード系テストと同じ考え方）
- **公開した関数・型の約束を固定する。** 未登録の入力に `nil` を返すのか既定値を返すのか、既存の値を上書きするのか素通しするのか。呼び側がそこに依存する
- エラー経路と境界（空入力、再実行・再配信、境界値）。既存テストが正常系だけのパッケージでは、変更した異常系がそのまま漏れる

十分（過剰の検出）:

- **実装を写しただけのテストを削る。** 表や分岐をテスト側で再定義して突き合わせるものは、実装を変えても一緒に変わるので何も固定していない
- 同じ分岐を層をまたいで二重に固定していないか。下位で固定した分類を上位でも全件並べ直すのは重複
- ライブラリの挙動（エラーのラップ、RPC フレームワーク、DB クライアントの仕様）を確かめるテストは、こちらの変更を固定しない
- テーブル駆動の行が、名前だけ違って同じ経路を通っていないか。件数ではなく通る経路の数で数える
- 固定したい 1 点に対して helper・mock・fixture が大きすぎないか

一貫性: 書き方（table-driven か、`assert` と `require` の使い分け、サブテスト名、golden の扱い）と置き場所を、同じパッケージの既存テストの実測に合わせる。外部依存を要するテストは、そのパッケージの `TestMain` の前提に沿わせる。前提を欠いたまま黙って通るテストは無いのと同じである。

報告には「変更した分岐 / 固定しているテスト / 赤を確認した方法」の対応を出し、対応が無い分岐はその旨を残す。

## 5. 動作確認

- 変更したパッケージのテストと lint を**実際に実行**し、結果を数字で控える（「通るはず」で済ませない）。実行するのは手元のテストと lint であり、GitHub の CI ではない（後述「CI を待たない」）
- lint の指摘は自分の変更ファイル起因か既存問題かを切り分け、既存問題には手を広げない
- **ガード系のテスト（不変条件の検査）は、検知したい状態で本当に落ちることまで確かめる**。本物を壊す代わりに、同型の「既にその状態にある対象」へ同じ検査を当てて反応することを見る（negative probe）。probe は使い捨てにする
- 生成物（mock、モデル、docs）は正規の生成コマンドで再生成し、差分が出ないこと（＝手編集していないこと）を確認する

ここで扱うのは手元で完結する確認である。実環境で動かして観測する確認は別物で、`../verification/SKILL.md` が扱う（本文の Verification 欄の書き方は `../pull-request/SKILL.md`）。SR の合否はこの節のローカルの結果で判断し、実環境の観測はそれとは独立に PR 本文へ積む。

### CI を待たない

**SR の検証はローカルで完結させる。** 変更したパッケージのテストと lint を手元で回した結果が根拠であり、GitHub の CI の完了は SR の前提にしない。CI が回り終わるまでターンを持ち続けると、依頼者は何も差し込めないまま待たされる。

CI の結果が必要な場合は**非同期で受ける**。`gh pr checks <n> --watch` などをバックグラウンドジョブとして起動し（Claude Code なら `run_in_background`）、**ターンは直ちに依頼者へ返す**。ジョブの完了通知が来た時点で結果を報告する。SR をサブエージェントに任せている場合、CI の監視はエージェントに持たせず親が起動する（エージェントは終了とともに消えるため）。

依頼者が明示的に「CI が通るまで待って」と言った場合を除き、CI の完了を待つことを理由にターンを終えない。バックグラウンドのジョブと完了の通知が無い環境では監視を起動せず、依頼者に求められた時点で `../ci-check/SKILL.md` に従って確かめる。

## 6. 意図しない差分

- diff に無関係ファイル・空白や改行だけの変更・一時ファイルが混ざっていないか
- 既存行を巻き添えにしていないか（末尾空白の除去なども含めて、依頼と無関係な既存行の変更は戻す）
- 機微データ・認証情報がテストデータ、ログ出力、その下流に連携される先に乗っていないか

## 7. 修正と報告

見つけた問題は観点ごとに独立したコミットに切って直す（コメント整理と挙動追加を混ぜない）。コミットメッセージは最終状態を説明し、「セルフレビュー対応」のような経緯は書かない。

push と PR 作成は親が行う（Draft の扱いは AGENTS.md の Git 節に従う）。エージェントは worktree にコミットを残すところまでにする。PR はまだ無ければ親が Draft で作る。

報告は観点ごとに三部で書く: **確認したこと（実測値つき）／見つけた問題／修正の diff**。コードの引用形式とパスのリンクは `../code-citation/SKILL.md` に従う。問題が無かった観点も「何をどう確認したか」を 1 行残す。未了事項は隠さず、PR 本文と報告の両方に書く。

報告の地の文は AGENTS.md の Writing 節に従う。三部の構成は崩さず、その中の文だけを合わせる。

## 8. PR 本文

本文の構成、言語、Verification 欄に何を書くかは `../pull-request/SKILL.md` に従う。SR から本文へ渡すもの、渡さないものは次のとおり。

- **未了事項**: 「1. 要件との突き合わせ」で裏付けが取れなかった項目を、本文のマージ条件に当たる欄（無ければ本文の末尾）と Verification 欄へ書く
- **ローカルの結果**: 「5. 動作確認」で実測したテストと lint は本文へ渡さない。CI が示すので、上の報告にだけ残す

渡された本文そのものも点検する。本文はレビュアーとチームが読む成果物で、差分と同じく SR の対象である。

- **最終状態との一致**: 本文の主張（変更の内容、影響範囲、Verification の観測値）を差分と実測に突き合わせる。直したのに古いままの記述、測った値と合わない記述を探す
- **書き方**: `../pull-request/SKILL.md` と AGENTS.md の Writing 節に照らす。作業の過程（評価やレビューで何が挙がったか、どう対処したか）を語る文、手元の環境の固有名（ローカルのテナント名やユーザー名）、変更の正しさに要らない確認の「未確認」を探す。過程を語る文は、その結果として残る事実（「〜は自動テストで固定していない。〜で確かめている」）に書き直すか、レビュアーに要らなければ削る

本文の修正は報告の「修正の diff」に本文の差分として書く。本文の編集は親が行う。

## UR への引き渡し

SR が終わったら実環境の検証を済ませ（`../verification/SKILL.md`）、依頼者の指示で **UR**（ユーザーレビュー）へ移る。UR の手順は `../user-review/SKILL.md` に従う。自分から UR を始めず、依頼者が「UR を」と告げてから入る。

UR では立場が入れ替わる。SR は自分が判断を下す段だが、UR で判断を下すのは依頼者であり、こちらは原文と背景を渡す側に回る。SR の結論（「問題ない」「良さそう」）と、SR で実測したこと・直したことを UR の場で繰り返さない（`../user-review/SKILL.md` の「各対象で述べること」）。

SR を経ていれば、UR の提示順で末尾に回せるものが決まっている。**生成物は UR の提示対象から外す。** 再生成して差分が出ないことを SR で確認した時点で、依頼者が原文に下せる判断は残らない。
