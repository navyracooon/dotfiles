# Verification（実環境での確認と記録）

実装が終わってから PR を Ready にするまでの間に、変更が実際に動くことを確かめ、**PR に記録する**段である。
PR 本文の Verification 欄に何を書くかは `../pull-request/SKILL.md` が定め、手元のテストと lint は `../self-review/SKILL.md` の「動作確認」が扱う。本スキルは、実環境で確かめる手順と記録の規則を持つ。

チーム固有の運用は `~/.config/ai/private/verification.md` があればそれに従う。無ければ PR だけに記録する。

## 1. 何を確かめるかを決める

チケットの AC を 1 項目ずつ見て、実環境でしか確かめられないものを選ぶ。手元のテストで固定済みの項目は、ここで繰り返さない。

**テストが通ったことは検証ではない。** テストは書いた人が想定した範囲しか踏まない。確かめるのは、実際の入口から実際のデータを通したときに意図した結果が出ることである。

## 2. 手段は軽いものから選ぶ

順に検討し、示せる最も軽いものを使う。

1. **デプロイせずにデータを通す**。ロジックに閉じた変更なら、検証に使うことが許されたデータを関数に流して数えるだけで足りる（やり方は `../pull-request/SKILL.md` の「デプロイせずにデータを通す」）
2. **ローカルの開発サーバ**。画面の見た目や操作は、手元で動かす開発サーバで足りることがある
3. **デプロイした環境**。1〜2 で示せないときだけ使う。使う環境は依頼者に確かめる

デプロイすれば確かに示せるという理由だけで 3 を選ばない。

リポジトリのドキュメントが既定の確認手順を定めているならそれに従うが、その手順がデプロイを指していても 1 や 2 が使えないかを先に見る。目的は「動いていることを確かめる」であって、既定経路を辿ることではない。

**Prod では確認しない。**

ローカル外のリソースに触る手段（デプロイ、クラスタ、クラウド DB）は、依頼者の明示の指示があるときだけ自分で実行する。指示がなければ、確認したいこと・コマンド・見るべき出力を提示して止める。

## 3. 変更前を同じ環境で再現する

修正と見た目の変更では、**変更前の状態を同じ環境で再現してから変更後を示す。** 同一データに対する前後の差が、変更が効いていることの証明になる。

裏を返すと、前後で差が出ない環境やデータでは何も証明できない。差が出る条件（時刻、対象レコード、データの形）を先に実測して選び、その条件も記録に書く。

前後を並べる典型は、変更前の checkout を別ポート・別インスタンスで同時に立て、同じ操作を両方に当てる形である。同じビルド・同じデータで 1 箇所だけが違う状態を作れるので、差分の原因が特定できる。

## 4. 見た目の主張は数値で裏取りする

スクリーンショットだけでは「そう見える」しか言えない。画面の変更では、**主張している性質を機械可読な値で取る。**

- 位置や寄せ: 要素の算出スタイルと、親要素との座標差
- 文言: 実際に描画された文字列
- 有効・無効: `disabled` と、操作が実際に呼ばれないこと
- 影響範囲: 変わっていないはずの要素が同じ値であること

数値と画像の両方を残す。数値は PR 本文に置く。画像の置き場は、チームの運用（非公開メモ）が無ければ PR 本文とし、添付は依頼者に預ける（自分では外部へアップロードしない）。

## 5. 示せていないことを書く

環境・権限・データの都合で確かめられない項目は必ず残る。**未了として書く。** 予定としてではなく現状として書き、なぜ確かめられないのかを添える。

「あとで確認します」は判断材料にならない。「モックが該当データを作らないため再現できず、ユニットテストで固定している」と書けば、レビュアーはその前提で承認するかを決められる。

**CI の結果は書かない。** CI が示しているので、本文で繰り返す意味がない。

## 6. 記録する

### PR の Verification 欄

3 点を書く。リポジトリに検証手順のドキュメントがあれば、その体裁を優先する。

- **環境**: 環境の名前、インスタンスの識別子、デプロイした成果物の識別子など、対象が一意に定まる形
- **実行したこと**: 環境変数の export を含め、そのまま再現できるコマンド。個人を特定しうる値（ユーザーの識別子など）はダミーに置き換える
- **観測されたものと、それが示すこと**: 応答やログの該当行、測った数値、そして変更の意図に対して何が示されたかを 1 文

## 7. 依頼者への報告

記録した先の**リンクを全部出す。** 複数の場所を直したなら全部を示す。片方だけ示すと、もう片方を直したことが依頼者に見えない。リンクの書き方は `../code-citation/SKILL.md` の「PR やチケットを報告するとき」に従う。

添付を依頼者に任せた画像があるなら、そのファイルも一緒に渡す。

この報告の地の文と、PR 本文に記録する文章は AGENTS.md の Writing 節に従う。

## 8. 順序

Verification は SR の後、UR の前に置く。
SR で手元のテストと lint を通し（`../self-review/SKILL.md`）、そのうえで実環境の確認結果を記録し、UR で依頼者に読んでもらう（`../user-review/SKILL.md`）。UR の場で PR 本文の Verification 欄が実測と合っているかを突き合わせられるのは、記録がこの順で先に済んでいるからである。
Ready にするのは依頼者の明示の指示を待つ。
