# Verification（実環境での確認と記録）

SR（`../self-review/SKILL.md`）で手元のテストと lint を通した後、UR（`../user-review/SKILL.md`）の前に、変更が実際に動くことを確かめて PR に記録する段である。記録の書式は `../pull-request/SKILL.md` の「Verification 欄」に従う。

## 1. 何を確かめるかを決める

チケットの AC を 1 項目ずつ見て、実環境でしか確かめられないものを選ぶ。手元のテストで固定済みの項目は繰り返さない。

**テストが通ったことは検証ではない。** テストは書いた人が想定した範囲しか踏まない。確かめるのは、実際の入口から実際のデータを通したときに意図した結果が出ることである。

## 2. 手段は軽いものから選ぶ

示せる最も軽いものを使う。共有環境に手を入れない手段を優先する。

1. デプロイせずにデータを通す（下記）
2. ローカルの開発サーバ。画面の見た目や操作はこれで足りることがある
3. デプロイした環境。1〜2 で示せないときだけ使い、使う環境は依頼者に確かめる

リポジトリの既定の確認手順がデプロイを指していても、1 や 2 が使えないかを先に見る。**Prod では確認しない。** ローカル外のリソースに触る手段は AGENTS.md の Workstyle 節に従い、指示がなければ確認したいこと、コマンド、見るべき出力を示して依頼者に預ける。

### デプロイせずにデータを通す

変更が純粋なロジック（対応付け、変換、判定）に閉じているなら、検証に使うことが許されたデータを、ブランチのその関数に流して結果を数える。使い捨てのプローブでよく、テストの数ケースより広くデータを踏める。データの許可の範囲と置き場は組織の規則に従う。プローブは消すので、同じ結果を再現する手段を記録に残す。

これで示せないのは配線と環境に依存する判定なので、記録では示せたことと分けて書く。

## 3. 変更前を同じ環境で再現する

修正と見た目の変更では、**変更前の状態を同じ環境で再現してから変更後を示す。** 同一データに対する前後の差が、変更が効いていることの証明になる。前後で差が出ない環境やデータでは何も証明できないので、差が出る条件（時刻、対象レコード、データの形）を先に実測して選ぶ。

典型は、変更前の checkout を別ポート・別インスタンスで同時に立て、同じ操作を両方に当てる形である。同じビルド・同じデータで 1 箇所だけが違う状態になり、差の原因が特定できる。

## 4. 見た目の主張は数値で裏取りする

スクリーンショットだけでは「そう見える」しか言えない。画面の変更では、主張している性質を機械可読な値で取る。

- 位置や寄せ: 要素の算出スタイルと、親要素との座標差
- 文言: 実際に描画された文字列
- 有効・無効: `disabled` と、操作が実際に呼ばれないこと
- 影響範囲: 変わっていないはずの要素が同じ値であること

数値は PR 本文に置く。画像は PR 本文に置く前提で依頼者に渡し、添付は依頼者に預ける（自分では外部へアップロードしない）。

## 5. 示せていないことを残す

環境、権限、データの都合で確かめられない項目は必ず残る。面倒だからと落とさず、できなかったことと理由を現状として記録する。「モックが該当データを作らないため再現できず、ユニットテストで固定している」のように書く。

## 6. 依頼者への報告

記録した先のリンクを `../code-citation/SKILL.md` に従って全部出し、添付を任せた画像があればそのファイルも渡す。
