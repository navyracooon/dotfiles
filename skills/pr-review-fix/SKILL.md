# PR レビュー対応の手順と PRF 体裁

## 全コメントの収集

`gh pr view --json reviews,comments` だけでは本文コメントを取り落とす。次の 3 面を必ず列挙する。

- inline レビューコメント: `gh api --paginate repos/{owner}/{repo}/pulls/{n}/comments`
- 本文（issue）コメント: `gh api --paginate repos/{owner}/{repo}/issues/{n}/comments`
- レビュー本体: `gh api --paginate repos/{owner}/{repo}/pulls/{n}/reviews`

収集したら、レビュアーごとの件数を数えて依頼者に示す。人間のコメントと、bot や AI のレビューは区別して扱う。

## 対応の順序と粒度

コメントは提示された順に 1 件ずつ扱い、重さで並べ替えない。依頼者が修正不要と判断したものは飛ばす。

**1 コメント = 1 コミット**に切り分ける。修正不要と判断した件はコミットを作らず、理由を報告に含める。指摘と無関係な修正は独立したコミットに切る。その指摘のコミット自身が入れた記述の直しは、`../pull-request/SKILL.md` の「Draft と push」に従って元のコミットへ畳む。

コミットメッセージは、指摘された事象と、なぜその修正が正しいかを述べる。レビュアー名や「レビュー指摘対応」とは書かない。

## 検証

主張は実測してから受け入れる。検証の結果、修正不要となることもある。

- ライブラリの挙動は使い捨ての probe で測り、測ったら消す
- 数値の主張は自分で計算し直す
- 「既存はこうなっている」という主張は、リポジトリを数えて件数を出す
- デザインの逸脱は、原本を引ける環境なら直接引く
- 相手の数値に誤りがあっても結論が変わらないなら、「結論は不変」と明記して受け入れる

検証できない主張は、できないと述べる。

## SR

全コメントのコミットを積み終えたら、PRF を出す前に `../self-review/SKILL.md` に従って SR を行う。対象は今回積んだ全コミット（`git diff origin/<branch>..HEAD`）である。

SR で見つけた問題の切り分けと畳み方は「対応の順序と粒度」と同じにする。畳んだ後は lint、テスト、生成物の確認をやり直し、測り直していない数値を報告に使わない。PRF の前に、SR の結果を観点ごとに 1 行（確認したこと、実測値、直した箇所）で置く。SR を経ていない PRF は出さない。

## PRF 体裁（PR Fix 体裁）

コメント 1 件ごとに、全件を次の三部構成で報告する。「PRF 体裁で」と呼ばれたときも、対応済みの内容をこの様式で出す。対象は PR 上のレビューコメントだけで、依頼者からの指示は通常の報告として書く。レビュアーへの返信は含めない。

    # {レビュアー}-{番号} → `{コミット SHA}` {一行の要約}

    ## コメント内容

    主張と根拠と提案を圧縮して要約する。丸写しにしない。

    ## 検証

    何をどう測り、結果がどうだったかを数値で述べる。
    「指摘は正確です」「一点だけ誤りがありますが結論は不変です」など、判定を明示する。

    ## 修正前後

    コードの原文を `../code-citation/SKILL.md` に従って載せる。
    ファイルが複数あるときは、ファイルごとに小見出しを付ける。
    テストの追加件数と内容、実行結果を末尾に書く。

## Push

**明示的な承認があるまで push しない。** 報告したら依頼者の指示を待つ。

指摘を受けて再修正したら、変更した箇所を含めて全件を PRF 体裁で出し直す。

## 最終段階

依頼者が「最終段階へ」と告げたら、push 前の最後の提示として、差分は再掲せずに次を出す。

- コミット 1 本ごとに、対応する指摘（または指摘外である旨）と一行の内容
- 修正不要と判断した指摘と、その理由の要約
- 未 push であることと、remote との差分の規模
- 検証の結果（テスト件数、lint、実測した数値）
- push 後に残る作業（別 PR に回した件、他リポジトリのマージ順など）

承認の言葉があるまで、この段階で止まる。
