# コードとファイルの示し方

## 引用

**説明にはコードの原文を出し、一字も書き換えない。** 原文は `git show <ref>:<path>` や `git diff <base>...<head> -- <path>` で取る。強調のマーカー（後述）を足すことだけは例外とする。

### 形式の選び方

hunk ごとに、消えた行があるかで選ぶ。ファイルが既存か新規かでは選ばない。

- 追加だけの hunk は、その言語のコードブロックで追加した行だけを示す。差分にしても `+` が付くだけで情報は増えず、シンタックスハイライトを失う。既存行は混ぜず、挿入位置は「`ListItems` の直後」のように散文で述べる
- 置換や削除を含む hunk は差分だけを示し、変更後の本文を併記しない。context は変更行の前後 1 行まで狭める
- 新規ファイルは本文で示す

1 つのファイルに両方の hunk が混ざるときは、ブロックを hunk の順に並べる。

### 引用範囲

判断に必要な範囲へ絞る。周辺の定型（import、テストの table 全件）は省き、省いたことを述べる。長い追加は要点の 1 件を引用し、残りは件数と内容を散文で述べる。

周辺の既存コードは引用しない。依頼者は常にコードを開いて読んでいる。挿入位置は散文で、隣接コードの慣習は実測した数値（「N メソッド中 M が doc を持ち、1 行が a 件」）で、比較対象は行リンクで示す。例外は、既存コードの中身そのものが論点で、原文を読まないと判断できないときだけである。

### 強調

背景色は使えない（HTML の `style` は落ち、ANSI エスケープは文字になる）。行末に `// ← 追加` のようなマーカーを対象言語のコメント構文で置くか、引用を該当ブロックだけに絞る。

## パスとリンク

応答に書いたパスは、作業ディレクトリ基準で自動的にリンクになる前提で書く。実体の無いリンクは誤った場所へ連れて行くので、無いより悪い。

- **パスは絶対パスで書く。** リポジトリ起点の相対パスは外れる。`git diff` や `grep` の出力から写したら、作業中の worktree の絶対パスを頭に付ける（`/Users/<you>/projects/myapp/internal/foo/foo.go:12`）。場所を示す必要がなければファイル名だけでよい
- 書く前に、そのパスが今あることを確かめる。scratchpad のようなセッション限りの一時ディレクトリは指さない
- 行は `:line`、範囲は `:開始-終了` で書く。**行番号は書くたびにそのファイルで測る。** 記憶や前回の応答から写すと、rebase や修正でずれる
- ラベルを付けるときは `[foo.go:12-14](/Users/<you>/projects/myapp/internal/foo/foo.go:12-14)` のように、ラベルをリンク先のファイル名と行に合わせる。省略はラベル側だけで行う
- コードブロックの中はリンクにならないので、開かせたいパスはブロックの外に出す
- PR と issue は完全な URL か `owner/repo#123` で書き、裸の `#123` は書かない。報告では、更新した先（PR、チケット、記録した場所）のリンクを全部出す
