# コードとファイルの示し方

## 引用

**説明にはコードの原文が必要である。** 散文だけで済ませない。原文は `git show <ref>:<path>` や `git diff <base>...<head> -- <path>` で取得し、一字も書き換えない。

### 形式の選び方

**「消えた行があるか」で選ぶ。** ファイルが既存か新規かでは選ばない。

**追加のみの変更**は、その言語のコードブロックで**追加した行だけ**を示す。差分にすると `@@` ヘッダと `+` 記号が付くだけで、変更前が空なので情報は増えず、シンタックスハイライトとコピーを失う。

既存行を同じブロックに混ぜない。混ぜるとどこからが追加なのか読み手には判別できず、`+` 記号を捨てた分の情報が欠ける。挿入位置は「`ListItems` の直後」のように散文で述べる。

**置換や削除を含む変更**は差分だけを示す。変更後の本文を別のブロックで併記しない。同じ行が 2 回出るだけで、重複の方が読み手の負担になる。

context は変更行の周辺 1 行まで狭める。前後の繋がりを見せるために context を広げない。

**形式はファイル単位ではなく hunk 単位で選ぶ。** 1 つのファイルに、置換を含む hunk と追加だけの hunk が混ざることは多い。置換を含む hunk だけを差分で切り出し、追加だけの hunk はコードブロックで示す。ファイル全体を 1 つの差分にまとめると、大部分を占める追加まで `+` 付きになり、シンタックスハイライトを失う。ブロックは hunk の順に並べ、追加だけのブロックには挿入位置を散文で添える（「`retryOnRateLimit` の直前に追加」）。

**新規ファイル**は本文（該当言語のコードブロック）で示す。

**生成物**（mock、モデル、docs、lock ファイル、生成された README やスキーマ）は引用しない。生成コマンドが入力から作るもので、読み手が原文に下せる判断がない。どのファイルが生成物かを一行述べるに留める。

**機械的な差分**（空白のみ、リネームのみ、一括置換）は、原文の全量を出さず形と規模だけ述べる。要約で済ませてよいのはこれだけである。

### 引用範囲

判断に必要な範囲へ絞る。周辺の定型（import、テストの table 全件）は省き、省いたことを述べる。これは追加のみの場合にも同じく効く。追加が長いときは全量を出さず、要点の 1 件を引用して残りは件数と内容を散文で述べる。

### 周辺の既存コードは引用しない

**依頼者は常にコードを開いて読んでいる。** 変更の前後にある既存コード、挿入位置の目印になる隣の行、同じファイルの兄弟実装を、位置を示すためや文脈を補うために引用しない。読み手の手元にすでにあるものを貼り直すだけで、応答が長くなる。

代わりに次の形で述べる。

- 挿入位置は散文で示す（「`ListItems` の直後」）
- 隣接コードの慣習は**実測した数値**で述べる（「N メソッド中 M が doc を持ち、行数は 1 行が a 件、2 行が b 件」）。コードを貼って読み手に数えさせない
- 比較対象のコードは行リンクで指す（「パスとリンク」に従う）。依頼者が必要と判断したときに自分で開ける

例外は、**その既存コードの中身そのものが論点になっている場合**である。挙動が非自明で、原文を読まないと判断できないときに限って引用する（下層が特定のエラーを吸収している、既存の実装が想定と違う形をしている、など）。位置や文脈の説明としては引用しない。

### 強調

背景色による強調はできない。HTML の `style` 属性は落ち、ANSI エスケープはコードブロック内で文字として扱われる。

強調が必要なら、行末に `// ← 追加` のようなマーカーを置く（対象言語のコメント構文を使い、構文として壊れない形にする）か、引用を該当ブロックだけに絞る。

## パスとリンク

### ファイルパスは常にリンクになる

パスを自動でリンクにするクライアントでは、**応答に書いたファイルパスは、リンクにする気がなくてもリンクになる。** 裸のパスも、バッククォートで囲んだパスもリンク化される。バッククォートは自動リンク化を防がない。

自動リンク化は**作業ディレクトリ基準で解決される**。そこに実体が無ければ壊れたリンクになり、依頼者がクリックすると何も開かないか、別のファイルが開く。

したがって規約は「パスをリンクにする」ではなく、**書いたパスが常に解決できる形になっていること**である。開けないリンクは、無いより悪い。誤った場所へ連れて行くためである。

### 絶対パスで書く

**パスは常に絶対パスで書く。** worktree でも本体クローンでも同じである。これだけで自動リンク化は正しく解決する。

```
/Users/<you>/projects/myapp/internal/foo/foo.go:12
/Users/<you>/projects/myapp-proj123/internal/bar/bar.go:40-43
```

**リポジトリのルート起点の相対パス（`internal/foo/foo.go`）を書かない。** 作業ディレクトリ基準で解決されるため外れる。リポジトリのディレクトリ名から始める形（`myapp/internal/...`）も環境によって通らないので使わない。

相対パスは `git diff`、`git show`、`grep` の出力から写すときに紛れ込む。出力を写したら、作業中の worktree の絶対パスを頭に付ける。

### 書く前に実体を確かめる

**リンクを書く応答では、そのパスが今あることを確かめてから書く。** `ls` か `grep -n` を 1 回通せば済む。行番号を実測するなら同じ操作で両方が確かめられる。

**セッション限りの一時ディレクトリ（Claude Code の scratchpad など）を指すリンクを残さない。** セッションごとに作られ、消える。前のセッションで作った worktree のパスは、会話を再開した時点で既に無いことがある。過去の応答や要約に出てくる `/private/tmp/.../scratchpad/wt/...` を写すのは、壊れたリンクを書く最短の道である。

**したがって、複数のセッションに跨る作業の worktree は永続する場所に作る。** 本体クローンの隣に `<リポジトリ>-<チケット>` の形で置く。scratchpad に作った worktree が消えていたら、`git worktree prune` してから同じブランチを永続パスへ作り直し、以降はそちらを指す。使い捨ての検証用なら scratchpad でよい。

ファイル名だけ（`bar.go`）を書くのは安全である。パスとして解決されないので壊れない。層や場所を示す必要がなければこれで足りる。

### 行と範囲

**行は `:line`、範囲は `:開始-終了` で書く。** 開いた先で該当範囲がハイライトされる。

行番号は**参照するファイルで実測する。** `grep -n` や `cat -n` で確かめ、記憶や差分のヘッダから推測しない。行がずれたリンクは、依頼者を別のコードの前に立たせる。

**同じ箇所を再掲するときも測り直す。** 前回の応答からリンクを写さない。rebase、依存 PR のマージ、自分の修正でファイルは動くため、一度当たっていたリンクが次の応答で外れる。

ブランチを取り違えない。PR の変更行を指すなら、その PR のブランチをチェックアウトした worktree の絶対パスで書く。本体クローンが別のブランチにあるなら、そこへのパスは当たらない。

### 明示的なリンク記法

絶対パスを裸で書けば解決するので、**リンク記法は短いラベルを付けたいときの選択**である。正しさのためではない。

```
[foo.go:12-14](/Users/<you>/projects/myapp/internal/foo/foo.go:12-14)
```

長い絶対パスを散文や表に何度も出すと読みにくいので、ラベルを付ける方が普通は読みやすい。見出しの中でも表のセルの中でもリンク記法は書ける。

**ラベルとリンク先を食い違わせない。** `[a.go:30](/絶対パス/.../b.go:30)` のように別のファイル名を表示すると、開く前に判断を誤らせる。ラベルはリンク先のファイル名と行に合わせる。

ラベルは `ファイル名:行` を基本とする。同名ファイルが複数ある場合（`foo.go` が層ごとにある、`bar.go` が interface と実装にある）は、層が分かる最小限を足す（`repository の bar.go`、`bar/bar.go`）。

**`...` で省略したパスをリンク先にしない。** `.../a.go:50` は構造上どこにも当たらない。省略したいならラベル側で省略し、リンク先は完全な絶対パスにする。

### コードブロックの中

**コードブロックの中は自動リンク化されない。** `git grep -n` の出力をそのまま貼る場合、そこに現れる相対パスは壊れないのでそのままでよい。

リンクとして開かせたいなら、ブロックの外の散文で絶対パスとして出す。

### PR と issue

PR と issue は完全な URL で書く。リポジトリは git remote から取る。`PR #123` のような裸の番号は書かない。別リポジトリのものは `owner/repo#123` の形で修飾する。

ローカルの絶対パスの方が依頼者の手数が少ないので、コードを指すときの既定はローカルである。GitHub の blob URL（`#L50-L56` 付き）は、依頼者以外に渡す場合や版を固定して示す必要がある場合に限る。

### PR やチケットを報告するとき

**依頼者に向けたリンクは通常のリンク記法で書く。** 開くためのものなので、コードブロックは要らない。

更新した先が複数あるなら**全部のリンクを出す。** PR とチケットの両方を直したなら両方を出す。片方だけ示すと、もう片方を直したことが依頼者に見えない。

**コードブロックで列挙するのは、レビューに出す直前に PR の一覧を求められたときと、UR の終了時（`../user-review/SKILL.md` の「終了」）だけである。** 他所へまとめて貼るための形なので、そのときはコードブロックに全件を並べ、通常のリンクも併記する。散文で各 PR に触れるときはリンク記法を使う。
