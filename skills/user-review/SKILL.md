# ユーザーレビュー（UR）の進め方

**UR**（ユーザーレビュー）は依頼者がレビュアーとして読む段である。書いた本人が自分の差分を点検する **SR**（セルフレビュー、`../self-review/SKILL.md`）とは立場が逆で、UR で判断を下すのは依頼者であり、こちらは判断材料を渡す側に回る。
自分のレビュー結果（良い、問題ない、修正すべき）を述べる場ではない。
判断は依頼者が下すので、そのために必要な原文と背景を出す。

SR と実環境の検証（`../verification/SKILL.md`）を先に済ませてから UR に入る。SR と検証の結果は提示に出さない（「各対象で述べること」）。検証結果は PR 本文へ記録済みなので、UR の最後に本文を突き合わせるときは Verification 欄も対象に入る。

併用する規範として `../code-citation/SKILL.md` を読む。

地の文（brief、処理の流れ、チェックポイントの各項目）は AGENTS.md の Writing 節に従う。本スキルが定める構成（番号付きの流れ、チェックポイントの箇条書き、表）は崩さず、その中の文だけを合わせる。終了時に示す PR 本文の構成は `../pull-request/SKILL.md` に従う。

## 最初の応答（対象 0）

**冒頭の概要は「対象 0」として独立した 1 応答にする。** 次の 3 つだけを出す。

**この PR の目的と解いた方法**：何が問題で、どの実装でそれを解いたかを述べる。レビュアーはここで差分全体の狙いを掴み、以降の 1 ファイルずつの提示をその文脈で読む。解いた方法は「どこに何を置いたか」まで書く（表を足した、計算をどの層へ移した、読み取りが何に変わった）。個々のファイルの説明は各対象の提示でするので、ここでは構造だけにする。検討の経緯と捨てた案は書かない。

**全体の見取り図**：コミット構成（SHA、件名、規模）またはファイル一覧と行数の表。依頼者が全体の大きさと分割を把握できる粒度にする。

**提示順とその根拠**：番号付きの表で、対象と位置づけを並べる。順序を設計した基準を一文で述べる。

**ここで応答を終え、合言葉を待つ。** 対象 0 に原文は出さない（出すものは目的・見取り図・提示順の 3 つだけで、コードは対象 1 以降で出す）。全体像と個々のファイルは読み手が別々に把握するものなので、同じ応答に詰めない。

対象 0 も他の対象と同じく `Current` で出し直し、番号（`0`）で戻れる。対象 1 で `Prev` と言われたら対象 0 を全量で出す。

チーム固有の運用は `~/.config/ai/private/user-review.md` があればそれに従う。

## 提示順の設計

重要度と理解しやすさのどちらを優先してもよいが、選んだ基準を宣言する。
既定の基準は依存の順であり、後続を読むために前提となるものを先に置く。

典型的な並べ方：

- **データ → 規則 → 変換 → 消費 → 保証**：スキーマや定義ファイルを持つ変更。規則の妥当性はデータの形を知らないと判断できない
- **入口 → 中核 → 周辺**：ハンドラや API の変更

次の 2 種類は末尾へ回す。

- 機械的な差分（空白のみ、リネームのみ、一括置換）
- 付随物（Makefile、lint 設定、依存の追加）

**ドキュメントの変更も提示対象にしない。** 索引への追記や記述の更新は、実装の説明を読めば内容が決まっているもので、原文を出して判断させる余地がない。見取り図に含め、提示順の表からは外す。

**テストも提示対象にしない。** テストが実装の変更を固定できているかは SR（`../self-review/SKILL.md`）で担保する。UR で見るのは実装であり、テストを並べると応答数が倍になって実装の流れが切れる。見取り図ではファイル数と行数だけ述べ、提示順の表からは外す。依頼者が明示的に求めたときだけ出す。

**生成物は提示対象にしない。** 生成物（mock、モデル、docs、lock ファイル、生成された README やスキーマ）は、正規の生成コマンドや CI のジョブが入力から作るものである。差分が出ないことは SR で再生成して確認済みなので、依頼者が読んで下せる判断はなく、読ませるのは時間の浪費である。レビューの対象は入力にあたる手で書いたソースだけにする。

見取り図では、どのファイルが生成物で何が生成したかを一行だけ述べ、提示順の表からは外す。依頼者が明示的に求めたときだけ出す。

## 1 応答の分量

**1 応答 1 ファイル**を守る。複数ファイルを 1 応答に詰めない。

ファイルが長い、または論点が複数ある場合は**要素ごとに分割**し、1 応答 1 要素にする。
分割の単位は、型の定義、読み込み、検証、生成、helper のように、読み手が一度に判断できるまとまりで切る。
分割したときは番号を振り（`3-1`、`3-2`）、その対象内で何が残っているかを示す。

同一ファイルの分割中は、合言葉で次の要素へ進む。ファイルを跨ぐときと同じ扱いにする。

## コードの引用

引用形式（差分と本文の使い分け、引用範囲）とパスをリンクにする書き方は `../code-citation/SKILL.md` に従う。UR に固有の点だけをここに置く。

- **1 応答につき原文を必ず出す。** 散文だけの応答で合言葉を待たない（対象 0 だけは例外で、原文を出さない）
- 生成物は提示しない。機械的な差分は末尾へ回し、形と規模だけ述べる（「提示順の設計」を参照）
- 修正して再提示するときは引用量を初回より減らさない（「提示中の修正」を参照）
- **提示のたびに行番号と実測値を測り直す。** 前回の応答から写さない

`Current`、`Prev`、修正後の再提示のいずれでも、行番号・引用範囲・地の文に書く数（メソッド数、行数、件数）をその場で取り直す。自分の修正、依存 PR のマージ、base への rebase で位置と件数はずれ、前回当たっていたリンクが次の応答で外れる。ずれた行番号は依頼者を別のコードの前に立たせるので、引用の中身が正しくても提示として失敗する。同じ対象を 3 回出すなら 3 回測る。

## 各対象で述べること

次の順で並べる。**短く保つ。**

1. **ファイル名**（パスのリンク）
2. **brief**。そのファイル・要素が元から何をするものかと、この変更が何をしたかを数行
3. **変更部分**の原文（差分。新規ファイルなら本文）
4. **処理の流れ**。引用した部分が何をしているかを `1.` `2.` の番号付きで順に書く
5. **なぜこうなっているかの補足**（必要なら。基本は書かない）

4 は原文を読む助けであって、行の言い換えではない。引用した処理を上から順に追い、何を受け取り、どこで分岐し、何を返すかを 1 項目 1 段階で書く。

**読み取り上の不都合は、流れの中に地の文で補う。** 分岐の条件が字面から読み取れない、名前と実際の役割がずれている、同じ判定が 2 度出てくる、といったものはその項目の中で一言添える。**注意書きとして別の見出しを立てない。** 注意書きはチェックポイントとは別物で、判断を仰ぐものではなく読みやすさのための補いである。

5 は基本的に書かない。4 で足りないときに限り、数行だけ添える。

**検証済みの事実は書かない。** SR（`../self-review/SKILL.md`）と実環境の検証（`../verification/SKILL.md`）は UR より前に済ませ、結果は PR 本文に記録してある。提示の中で繰り返さない。検証は内部で済ませ、提示には出さない。ただし提示のために測った行番号や件数は、地の文の数値としてそのまま使う。

**周辺コードを長く引かない。** 変更前の原文、呼び出し元、型定義、生成される値を並べて説明を積み上げない。出すのは変更部分だけで、役割は 2 の数行で足りる。依頼者が必要と判断すれば質問が来るので、そこで初めて掘る。

推測を断定として書かない。
自分の判断を述べる場合は、依頼者の判断と区別できる形（「範囲外と判断するなら落とせます」）にする。

## チェックポイント（判断が分かれるものだけ）

出すのは、**同じ情報を見ても人によって結論が変わるもの**だけである。依頼者に判断を仰ぐ場であって、選択の一覧を作る場ではない。

除くものが 2 種類ある。

- **一通り**: 型、API の形、生成物、既存の呼び出し規約がその形を強制している。他の書き方だとコンパイルが通らない、既存の呼び出し側が壊れる、整形器や lint が書き換える、リポジトリに前例が 1 つしかない（**件数を実測して示す**）
- **選択だが答えがほぼ決まっている**: 書き方は複数あるが、費用を並べれば結論が一つに落ちる。重複した 3 関数を 1 つに畳む、同じ構造体の組み立てを helper に出す、といったもの

**後者を落とすのが難しい。** 自分が選んだ以上どれも「選んだ形」に見えるので、選択であることだけを根拠に並べると、本当に分かれる論点がその中に埋もれる。判定は**対案の利点を 1 行で書けるか**で行う。書けないなら落とす。自分が選んだ形の裏返し（「選ばなかったぶんの費用」）しか書けないものも落とす。

残るのは、**不確かな前提を置いたまま通したもの**、**暗黙の不変条件に依存させたもの**、**層やスコープの線引き**、**エラーを落とすか続けるか**、**チケットの指定と実装が食い違うもの**あたりである。

**0 件になる対象は普通にある。** そのときは節ごと省く。「特にありません」とも書かない。ひねり出して埋めない。

処理の流れを述べたあと、残ったものを最後に置く。1 件ごとに小見出しを立て、次を**箇条書きで**出す。地の文の段落で書かない。

- **該当箇所**: 差分から数行だけ抜いた原文。上の 3 と重複するが、判断の対象を目の前に置くためなので省かない
- **選んだ形**: 1〜2 行
- **対案**: 代わりに採りうる形を 1 行
- **対案の利点**: それを採ると何が良くなるかを 1 行
- **対案の欠点**: それを採ると何を失うかを 1 行

5 つは並列に置く。**利点と欠点を必ず両方書く。** 片方だけでは依頼者が比較できず、判断を仰いだことにならない。

**自分の選択を弁護する文に混ぜない。** 「〜だが費用が大きい」「〜と言う人もいるだろう」のような書き方をせず、利点は利点として、欠点は欠点として別の項目に置く。判断を下すのは依頼者なので、両方の形が同じ強さで並んでいる必要がある。

迷ったときは出す。判断の余地があるものを黙って通す方が、逆より損が大きい。ただし「迷った」は対案の利点が書けたときに限る。

## 合言葉と進行

各応答の末尾に、合言葉で次へ進むこと、および次の対象名を一行で示す。

`Next`、`Viewed`、`次へ`、`OK`、およびそれに準ずる短い肯定を、次へ進む合図として扱う。
**合言葉が来るまで次へ進まない。**

`Current`、`もう一度`、`再掲` は `Next` と対になる合言葉で、進まずに現在の対象をそのまま出し直す。
初回と同じ構成・同じ引用量で全量を出す。要約したり、前回の要点だけを述べたりしない。

`Prev`、`前へ`、`戻る` は 1 つ前の対象へ戻り、`Current` と同じ全量で提示する。
戻った先が現在の対象になるので、以降の `Next` はそこから 1 つ進む。飛ばした対象を読み直すために使われるので、要約で応じない。

合言葉以外の応答（質問、指摘、修正依頼）が来たときは、その対象に留まる。
質問に答え、修正が必要なら修正し、再度その対象を提示してから合図を待つ。

依頼者が「N へ飛んで」「あれをもう一度」と指定したときは、その対象へ移る。順序に固執しない。

## 提示中に届く非同期の結果

CI やバックグラウンドジョブの結果が UR の途中で届いたときは、**待たずにその場で差し込む**。結果は短く報告してから提示を続ける。

赤が出て修正が必要になった場合は「提示中の修正」と同じ扱いにする。修正して、その対象を全量再提示し、合言葉を待つ。

CI の完了を待つために提示を止めない。依頼者が次へ進めるかどうかは依頼者が決める。完了の通知が届かない環境では、結果を待たずに提示を続け、依頼者に求められた時点で確かめる。

## 提示中の修正

提示の途中で依頼者が修正を求めた場合、修正してから、その対象を**最初と同じ形で全量再提示する**。

- 修正箇所だけの差分説明で済ませない
- 引用の量を初回より減らさない
- 修正が及んだ要素は、原文もその周辺の説明も出し直す。「前回から変わりません」で飛ばさない

例外として、**提示済みで、かつ修正の影響を受けていない要素は飛ばしてよい**。飛ばした要素は名前だけ挙げる。
影響の有無は原文の一致だけで判断しない。下流を直した結果として上流の挙動や前提が変わったなら、原文が同じでも再提示する。
まだ提示していない要素は、修正の影響と無関係にそのまま順に提示する。

再提示のあとは合言葉を待つ。修正したからといって次の対象へ自分から進まない。

**提示中に入れた修正は SR を通っていない。** Ready にする前に、その追加コミットを `../self-review/SKILL.md` の「SR を通すのは Ready までに積んだ全コミットである」に従って SR へ回す。

レビューが始まる前（Draft）であれば `--fixup` と `rebase --autosquash` で該当コミットへ畳む。
レビューが始まっている場合は追加コミットで積む。
どちらにしたかを述べる。

修正後はテストと lint を回す。**結果は提示に書かない**（「各対象で述べること」の検証済みの事実と同じ扱い）。落ちた場合だけ、落ちたことと対処を述べる。

## 終了

全対象を提示し終えたら、次を出す。

- 提示した対象の一覧と、依頼者から指摘が出た件の一覧
- 提示中に加えた修正と、その畳み先
- 未検証のまま残っている点
- 次の作業（push、Ready への変更、後続 PR）

このとき差分は再掲しない。
Ready への変更は、依頼者の明示的な指示を待つ。push は AGENTS.md の Git 節に従う。

**Ready（Draft の解除）は UR を終えてからに限る。** 依頼者が UR 前に Open を指示しても、その対象の UR が済んでいなければ Open にしない。UR を通す前にレビュアーへ出してしまうと、UR で入れる修正が force-push になる。
Open にする範囲は、**UR を終えたチケットの PR だけ**である。依頼者の「全部」は、その意味に取る。他チケットの PR は、同じ親チケットに属していても、それぞれの UR が済むまで Draft のままにする。
1 チケットが複数リポジトリに跨るときは、そのチケットに属する PR を数え上げて全て Open にする。数が合っているかを Open の前に一度読み上げる。

**PR のリンクを列挙するときはコードブロックに入れ、通常のリンクも併記する。** 形式は `../code-citation/SKILL.md` の「PR やチケットを報告するとき」に従う。PR 本文の全文は逆に、コードブロックへ入れずそのまま出す。

**そのうえで最後に PR 本文の全文を示す。** 本文そのものの書き方は `../pull-request/SKILL.md` に従う。
UR の途中で入れた修正が本文へ反映されているかを、依頼者がその場で確かめられるようにするためである。
提示する前に、本文と最終状態が食い違っていないか自分で突き合わせる。実装を変えたのに本文が古い、検証の記述が実測と合わない、解消済みのマージ条件が残っている、などを見る。
食い違いがあれば本文を直し、直した後の全文を出す。何を直したかは一行で添える。

- **関連する PR は全部出す。** 複数リポジトリ・複数 PR にまたがる場合、UR で扱った 1 本だけでなく、その作業に属する PR の本文をすべて全文で示す。番号と一行だけの要約で済ませない
- **コードブロックに入れない。** 本文は Markdown としてレンダリングされる形で出す。全体を ``` で囲うと読み手が本文を読めない
- **英語だけの本文には和訳を添える。** そのリポジトリの慣習が英語のみでも、提示のときは対応する日本語を段落ごとに付ける（本文自体を書き換える必要はない）
- **本文を修正したら、修正後の全文をもう一度すべて出す。** 差分だけの提示で済ませない。複数 PR のうち 1 本を直した場合も、直した PR は全文を出し直す
