# ユーザーレビュー（UR）の進め方

UR は依頼者がレビュアーとして読む段である。判断を下すのは依頼者で、こちらは判断に必要な原文と背景を渡す側に回る。自分のレビュー結果（良い、問題ない、修正すべき）は述べない。

SR（`../self-review/SKILL.md`）と Verification（`../verification/SKILL.md`）を済ませてから入る。引用とリンクは `../code-citation/SKILL.md` に従う。

## 最初の応答（対象 0）

対象 0 は独立した 1 応答にし、次の 3 つだけを出す。原文は出さない。

- **目的と解いた方法**: 何が問題で、どの実装で解いたか。どこに何を置いたか（表を足した、計算をどの層へ移した）まで書くが、ファイルごとの説明と検討の経緯は書かない
- **見取り図**: コミット構成（SHA、件名、規模）またはファイル一覧と行数の表
- **提示順**: 番号付きの表で対象と位置づけを並べ、順序の基準を一文で述べる

ここで応答を終え、合言葉を待つ。

## 提示順の設計

既定の基準は依存の順で、後続を読む前提になるものを先に置く。重要度や理解しやすさを優先してもよいが、選んだ基準を宣言する。

- データ → 規則 → 変換 → 消費 → 保証: スキーマや定義ファイルを持つ変更
- 入口 → 中核 → 周辺: ハンドラや API の変更

機械的な差分と付随物（Makefile、lint 設定、依存の追加）は末尾へ回す。

ドキュメント、テスト、生成物は提示順に入れず、見取り図でファイル数と行数（生成物なら何が生成したか）だけ述べる。ドキュメントは実装を読めば内容が決まり、テストの十分さと生成物の再生成は SR で確かめてある。依頼者が求めたときだけ出す。

## 1 応答の分量

**1 応答 1 ファイル。** 長いファイルや論点が複数あるファイルは、読み手が一度に判断できるまとまり（型の定義、読み込み、検証、helper など）で要素に分け、1 応答 1 要素にする。分けたら番号を振り（`3-1`、`3-2`）、その対象に残っている要素を示す。

## 各対象で述べること

短く保ち、次の順で並べる。

1. ファイル名（パスのリンク）
2. brief: そのファイル・要素が元から何をするものかと、この変更が何をしたかを数行
3. 変更部分の原文（対象 0 以外は必ず出す）
4. 処理の流れ: 引用した部分を上から追い、何を受け取り、どこで分岐し、何を返すかを `1.` `2.` で 1 項目 1 段階ずつ書く。行の言い換えではなく、原文を読む助けにする
5. なぜこうなっているかの補足（4 で足りないときだけ数行）

読み取り上の不都合（分岐の条件が字面から読めない、名前と役割がずれている、同じ判定が 2 度出る）は、4 の該当項目に地の文で一言添える。注意書きの見出しは立てない。

行番号と地の文に書く数（メソッド数、行数、件数）は、提示のたびに測り直す（`../code-citation/SKILL.md` の「パスとリンク」）。

**SR と Verification で確かめた事実は書かない。** 結果は PR 本文に記録してある。提示のために測った行番号や件数は、地の文の数値として使ってよい。

周辺コード（変更前の原文、呼び出し元、型定義）を並べて説明を積み上げない。依頼者が必要とすれば質問が来る。推測を断定で書かず、自分の判断は依頼者の判断と区別できる形（「範囲外と判断するなら落とせます」）にする。

## チェックポイント

出すのは、同じ情報を見ても人によって結論が変わるものだけである。次の 2 種類は除く。

- 一通りしかないもの: 型、API の形、生成物、既存の呼び出し規約がその形を強制している。他の書き方ではコンパイルが通らない、呼び出し側が壊れる、整形器が書き換える、前例が 1 つしかない（件数を実測して示す）
- 選択だが答えがほぼ決まっているもの: 重複した 3 関数を 1 つに畳む、同じ組み立てを helper に出す、など

**判定は、対案の利点を 1 行で書けるかで行う。** 書けないもの、自分が選んだ形の裏返ししか書けないものは落とす。残るのは、不確かな前提を置いたまま通したもの、暗黙の不変条件への依存、層やスコープの線引き、エラーを落とすか続けるか、チケットの指定と実装の食い違いあたりである。対案の利点が書けて迷うものは出す。

0 件の対象は普通にあり、そのときは節ごと省く（「特にありません」とも書かない）。

処理の流れの後に、1 件ごとに小見出しを立て、次の 5 つを並列の箇条書きで出す。

- **該当箇所**: 差分から数行だけ抜いた原文
- **選んだ形**: 1〜2 行
- **対案**: 1 行
- **対案の利点**: 1 行
- **対案の欠点**: 1 行

利点と欠点は必ず両方書き、それぞれの項目に分けて置く。「〜だが費用が大きい」のように自分の選択を弁護する文に混ぜない。

## 合言葉と進行

各応答の末尾に、合言葉で次へ進むことと次の対象名を一行で示す。

- `Next`、`Viewed`、`次へ`、`OK` など短い肯定: 次の対象へ進む。来るまで進まない
- `Current`、`もう一度`、`再掲`: 現在の対象を初回と同じ構成・同じ引用量で出し直す
- `Prev`、`前へ`、`戻る`: 1 つ前の対象を同じく全量で出し、そこを現在の対象にする。対象 1 からなら対象 0 を出す
- 「N へ飛んで」: その対象へ移る

要約や前回の要点だけで応じない。合言葉以外（質問、指摘、修正依頼）はその対象に留まって答え、必要なら修正し、その対象を再提示して合図を待つ。

CI やバックグラウンドジョブの結果が途中で届いたら、短く報告して提示を続ける。修正が要るなら「提示中の修正」と同じ扱いにする。CI の完了を待つために提示を止めない。

## 提示中の修正

依頼者が修正を求めたら、修正してから、その対象を最初と同じ形で全量再提示し、合言葉を待つ。修正箇所だけの説明で済ませず、引用量を初回より減らさない。

提示済みで修正の影響を受けていない要素は、名前だけ挙げて飛ばしてよい。原文が同じでも、下流の修正で挙動や前提が変わったなら再提示する。

修正後はテストと lint を回し、落ちたときだけ対処とともに述べる。修正コミットを畳むか積むかは `../pull-request/SKILL.md` の「Draft と push」に従い、どちらにしたかを述べる。提示中の修正は SR を通っていないので、Ready の前に SR へ回す。

## 終了

全対象を提示したら、差分は再掲せずに次を出す。

- 提示した対象と、依頼者から指摘が出た件の一覧
- 提示中に加えた修正と、その畳み先
- 未検証のまま残っている点
- 次の作業（push、Ready、後続 PR）

**Ready（Draft の解除）は UR を終えてからに限り、依頼者の明示の指示を待つ。** UR 前に Open を指示されても、UR が済んでいなければ Open にしない。UR の修正が force-push になる。Open にするのは UR を終えたチケットの PR だけで、依頼者の「全部」もその意味に取る。1 チケットが複数リポジトリにまたがるときは、属する PR を数え上げ、数を読み上げてから全て Open にする。

最後に PR 本文の全文を示す。本文の書き方は `../pull-request/SKILL.md` に従う。出す前に、本文が最終状態と食い違っていないか（実装を変えたのに本文が古い、Verification 欄が実測と合わない、解消済みのマージ条件が残っている）を突き合わせ、直したなら何を直したかを一行添える。

- 関連する PR は、複数リポジトリにまたがっても全部の本文を全文で出す
- 本文はコードブロックに入れず、Markdown としてレンダリングされる形で出す
- 英語だけの本文には、段落ごとに和訳を添える（本文自体は書き換えない）
- 本文を修正したら、修正後の全文を出し直す
