# PR の作り方と本文の書き方

本文の地の文は AGENTS.md の Writing 節に従う。本文を依頼者へ提示する形は `../user-review/SKILL.md` の「終了」が定める。

## 本文はレビュアー宛の文章である

**PR 本文は自分の作業メモではない。** 読み手はこの変更を承認するかを判断する人で、知りたいのは「これは何で、なぜ必要で、何がどこまで確かめられているか」である。

したがって次を書かない。

- 「後でここに記録します」「次はこれをやります」のような自分への予定
- 検討の経緯、途中で捨てた案、レビュー中に方針が変わった話
- ブランチ内の before / after（最終状態だけを書く）

未了のことは予定として書くのではなく、**レビュアーが判断に使える事実として書く。** 「検証環境では未検証」と書けば、レビュアーはその前提で承認するかを決められる。「あとで検証環境で叩いて記録します」は、決めるための材料になっていない。

## 構成はリポジトリのテンプレートに従う

テンプレートがあるならその見出しと順序をそのまま使う。欄を消さない。該当しない欄には「該当なし」と理由を書く。チェックボックスは、確認したものだけを埋め、埋めた根拠を 1 行添える。

変更内容は最終状態を述べる。理由は、その変更が必要な理由と、他の形を採らなかった理由のうちレビュアーが疑うところを述べる。マージの前提（依存 PR、マイグレーションの適用、環境変数の設定）は、テンプレートにマージ条件に当たる欄があればそこへ集め、本文の散文へ埋めない。

## 言語

リポジトリの慣習に合わせる。**複数の言語を併記する形が使われているなら、その形式に従う**。

慣習の言語が依頼者の言語と違い、併記もしない場合は、本文は慣習の言語のままにし、依頼者へ提示するときにだけ訳を付ける（`user-review` の「終了」）。

## Verification 欄

検証を書く欄（以下 Verification 欄）の名前はテンプレートに従う。テンプレートに無ければ見出しを立てる。

**Verification はテストコードの説明ではない。** テストの一覧や「旧実装では n 件落ちる」は、実装がテストの通りに動くことしか言っていない。テストは現実のシナリオを網羅していないので、最終的な根拠は実環境の観測に置く。ここに書くのは「どの環境で、何を実行して、何が観測されたか」である。

**テストと lint が通ることは本文に書かない。** CI が示しているので、本文で繰り返す意味がない。手元で実行した結果も同じで、そのための欄を足して移すのではなく落とす。Verification に残すのは CI では回らない検証、すなわちデータを通した結果と実環境で観測したものだけである。

書く 3 点は次のとおり。リポジトリに検証手順のドキュメントがあれば、その体裁を優先する。

- **実行した環境**: 環境の名前、インスタンスの識別子、デプロイした成果物の識別子など、対象が一意に定まる形で書く。デプロイした成果物は、その識別子から PR の最終コミットが辿れるようにする
- **実行したコマンド**: 環境変数の export を含め、そのまま貼って再現できる形で書く。個人を特定しうる値（ユーザーの識別子など）はダミーに置き換える
- **観測された出力と、それが示すこと**: 応答やログの該当行を引用し、変更の意図に対して何が示されたかを 1 文で書く

バグ修正なら、**修正前の壊れた挙動を同じ環境で再現してから**修正後を示す。同一データに対する前後の差が、修正が効いていることの証明になる。裏を返すと、前後で差が出ない環境やデータでは何も証明できない。差が出る条件（時刻、対象レコード）を先に実測して選び、その条件も本文に書く。

### 手段は軽いものから選ぶ

何で検証するかは `../verification/SKILL.md` の「手段は軽いものから選ぶ」に従う。**共有環境に手を入れない手段を優先する。**

### 実行は依頼者に預ける

検証の実行はローカル外のリソースに触る。**明示の指示がない限り自分で実行しない。** 確認したいこと、そのためのコマンド、見るべき出力を提示して止め、実行を依頼者に預ける。読み取りだけの操作（クラスタやクラウド上の DB の読み取り）も同じ扱いにする。

コマンドと手順を本文に置く場合は、レビュアーが読んで意味のある形にする。自分が後で実行するための控えとして置くのではなく、「この環境でこれを叩けば同じことが確かめられる」と示すために置く。

### デプロイせずにデータを通す

変更が純粋なロジック（対応付け、変換、判定）に閉じているなら、実環境に配置しなくてもデータは通せる。検証に使うことが許されたデータを、ブランチのその関数にそのまま流して結果を数える。使い捨てのプローブでよく、テストの数ケースより広くデータを踏める。データの許可の範囲と置き場は組織の規則に従う。プローブは消すので、同じ結果を再現する手段は本文に残す。

ここで示せないのは transport（配線）と環境に依存する判定なので、**示せたことと示せていないことを節に分けて書く。**

### 検証できないときは未了と書く

実環境の確認はフローの一段であり、面倒だからと落とさない。ただし環境、権限、データの都合で今できないことはある。環境のデータでは、修正が効く場面を再現できないこともある。

そのときは Verification を埋めた気にならず、**できなかったことと理由を書く**。予定ではなく現状として書く。チーム固有の扱いは `~/.config/ai/private/pull-request.md` があればそれに従う。

## 1 チケットを複数 PR に割るとき

**前提 PR が要らない形に整えるのが最良である。** 各 PR が単独でビルドでき、CI が緑で、単独で動作確認できる状態を目指す。

前提 PR がある形は、レビュアーに余計な判断を要求する。どれから見るのか、CI が赤いのは想定内なのか、この PR だけで何が確かめられたのか。そして「ローカルで前提 PR の A と B をマージして確認しました」という検証は、A か B に問題が見つかった時点で前提ごと崩れる。

チケットの依存関係から素直に実装すると前提 PR が生まれるが、実装側で解ける。

- **先に空のハコを置く。** 全体の形を決めてから、各層の空の実装（エラーを返す、何もしない）を最初の PR で入れ、後続のチケットで中身を埋める
- **共通しそうな部分を先に終わらせる。** 環境変数の追加、設定、型の追加などは、それを使うチケットより先に単独の PR で入れる
- **依存する箇所はエラーかスキップにしておく。** 未実装の依存先を呼ぶ箇所は、その時点ではエラーを返すか処理を飛ばす形にし、依存先が入ってから実装する

分割を決める前に、この整理ができないかを検討する。できずに前提 PR が残る場合は、**各 PR の本文に「単独で何が確かめられていて、何が前提の後でしか確かめられないか」を書く**。CI が赤い理由も書く。

チケットの分割そのものに無理がある場合はそう述べる。ただし実装側で解ける余地を検討したうえで言う。

前提 PR が残るときも、リポジトリの慣習がスタックでなければ、PR はスタック（前提 PR のブランチの上に切る）せず、base 基点の兄弟として並べる。先行 PR がマージされたら後続を base へ rebase し、rebase が無衝突で通ってもビルドを回す（先行 PR の改名と後続の追加行がぶつかることがある）。マージの順序は、マージ条件に当たる欄（無ければ本文の末尾）に書く。

## Draft と Open

PR は Draft で作る。Open にするのは UR を終えてからで、依頼者の明示的な指示を待つ（`../user-review/SKILL.md` の「終了」）。

レビューが始まる前（Draft）なら、push も rebase も force-push も自由に行う（AGENTS.md の Git 節）。始まった後は force-push せず、追加コミットで積む。
