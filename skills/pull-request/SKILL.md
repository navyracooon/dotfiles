# PR の作り方と本文の書き方

## 本文はレビュアー宛の文章である

**PR 本文は自分の作業メモではない。** 読み手は承認するかを判断する人で、知りたいのは「これは何で、なぜ必要で、何がどこまで確かめられているか」である。

次を書かない。

- 「後で記録します」「次はこれをやります」のような自分への予定
- 検討の経緯、捨てた案、レビュー中に方針が変わった話、ブランチ内の before / after
- テストと lint が通ったこと（CI が示している）

未了のことは、レビュアーが判断に使える現状として書く。「検証環境では未検証。理由は〜」と書けばその前提で承認を決められるが、「あとで検証環境で叩きます」は材料にならない。

## 構成と言語

テンプレートがあるなら、見出しと順序をそのまま使う。欄を消さず、該当しない欄には「該当なし」と理由を書く。チェックボックスは確認したものだけを埋め、根拠を 1 行添える。

変更内容は最終状態を述べる。理由は、変更が必要な理由と、他の形を採らなかった理由のうちレビュアーが疑うところを述べる。マージの前提（依存 PR、マイグレーション、環境変数）は、マージ条件に当たる欄があればそこへ集める。

言語はリポジトリの慣習に合わせ、複数言語の併記が慣習ならその形に従う。慣習の言語が依頼者の言語と違っても本文は慣習のままにし、訳は依頼者へ提示するときにだけ付ける（`../user-review/SKILL.md` の「終了」）。

## Verification 欄

欄の名前はテンプレートに従い、無ければ見出しを立てる。

**Verification はテストの説明ではない。** テストの一覧や「旧実装では n 件落ちる」は、実装がテストの通りに動くことしか言わない。ここには CI では回らない検証、つまり実環境で観測したものとデータを通した結果だけを書く。何をどう確かめるかは `../verification/SKILL.md` に従う。

書くのは次の 3 点である。リポジトリに検証手順のドキュメントがあれば、その体裁を優先する。

- 環境: 環境の名前、インスタンスや成果物の識別子など、対象が一意に定まる形。成果物の識別子から PR の最終コミットが辿れるようにする
- 実行したこと: 環境変数の export を含め、そのまま貼って再現できるコマンド。個人を特定しうる値はダミーに置き換える
- 観測されたものと、それが示すこと: 応答やログの該当行、測った数値と、変更の意図に対して何が示されたかを 1 文

修正なら、差が出る条件（時刻、対象レコード）と変更前の観測も書く。示せたことと示せていないことは節を分け、示せていないことには理由を添える。

## 1 チケットを複数 PR に割るとき

**前提 PR が要らない形に整えるのが最良である。** 各 PR が単独でビルドでき、CI が緑で、単独で動作確認できる状態を目指す。前提 PR のある形は、どれから見るか、CI の赤が想定内かといった判断をレビュアーに求め、「ローカルで A と B をマージして確認した」という検証は A か B の修正で崩れる。

チケットの依存から素直に実装すると前提 PR が生まれるが、実装側で解ける。

- 先に空のハコを置く。各層の空の実装（エラーを返す、何もしない）を最初の PR で入れ、後続で中身を埋める
- 共通しそうな部分（環境変数、設定、型）を、それを使うチケットより先に単独の PR で入れる
- 未実装の依存先を呼ぶ箇所は、エラーを返すか処理を飛ばす形にしておく

それでも前提 PR が残るなら、各 PR の本文に、単独で確かめられたことと前提の後でしか確かめられないこと、CI が赤い理由を書く。チケットの分割そのものに無理があるなら、実装側で解ける余地を検討したうえでそう述べる。

リポジトリの慣習がスタックでなければ、PR は前提 PR のブランチの上に切らず、base 基点の兄弟として並べる。先行 PR がマージされたら後続を base へ rebase し、無衝突でもビルドを回す。マージの順序はマージ条件の欄（無ければ本文の末尾）に書く。

## Draft と push

PR は Draft で作る。Open にする条件は `../user-review/SKILL.md` の「終了」が定める。

修正は `--fixup` と `rebase --autosquash`（HEAD なら `--amend`）で該当コミットへ畳む。畳み先がまだ push していないコミットなら、いつでも畳んでよい。push 済みのコミットへ畳む force-push は、レビューが始まる前だけ行う（AGENTS.md の Git 節）。始まった後は追加コミットで積む。他のスキルで修正を畳むか積むかは、この規則で決める。
